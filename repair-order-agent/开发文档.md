# 维修语音助手开发文档

## 项目目录决策

不再新建第三个顶层项目文件夹。

目前已有：

- `repair-order-agent`：维修订单业务逻辑
- `voice-agent-demo`：实时 ASR、TTS、VAD 和网页语音链路

后续将 `repair-order-agent` 作为正式主项目，逐步把
`voice-agent-demo` 的实时语音能力整合进来。
`voice-agent-demo` 保留为旧版原型和迁移参考。

继续复制新项目会产生多份配置、依赖和测试，增加维护及部署成本。

## 建议的最终目录

```text
repair-order-agent/
  app/
    domain/
      repair_order.py       # 维修订单、槽位和状态定义

    services/
      extractor.py          # JSON 结构化信息抽取
```

## 整合原因

目前 `voice-agent-demo` 通过修改 `sys.path` 引用旁边的
`repair-order-agent`。这适合原型验证，但不适合正式部署：

- 启动目录变化可能导致包无法导入。
- 两个项目分别维护配置和依赖，容易不一致。
- 部署时必须同时复制两个目录。
- 后续难以判断功能应该修改在哪一个项目。

整合后，业务逻辑、语音链路、配置、录音资源、数据库和测试均由
`repair-order-agent` 统一管理。

## 安全迁移方式

1. 使用 Git 分支保存当前可运行版本，不复制新的项目目录。
2. 在 `repair-order-agent` 中建立完整应用结构。
3. 分模块迁移 `voice-agent-demo` 的 ASR、TTS、VAD、Web 和编排代码。
4. 每迁移一部分就运行现有单元测试和真实粤语对话测试。
5. 整体测试通过后，将 `voice-agent-demo` 标记为旧原型。
6. 最终生产环境只启动和部署 `repair-order-agent`。

## 当前结论

不新建新的项目文件夹。后续以 `repair-order-agent` 为唯一正式主项目，
逐步合并实时语音能力，并保留 `voice-agent-demo` 作为迁移期间的参考。

## 下一版业务架构

本节记录 2026-09-30 确定的下一版电话维修订单流程。

整体方向比当前原型更接近生产电话系统，重点改进字段优先级、结构化抽取、
精准纠错、字段校验、失败重试、语言跟随和人工升级。

### 1. 开场与字段优先级

维修热线采用自然、开放式开场：

> 你好，有咩可以帮到你？

不默认使用“问候 + 问姓名”的绑定话术。客户通常会在第一句话直接描述故障，
先让客户说明来意更自然，也更容易首次获得维修内容。

收集字段的默认优先级：

```text
repair → phone/ANI → name
```

- 缺少 `repair`：先询问维修设备和故障情况。
- 缺少 `phone`：优先确认 ANI 来电号码，否则询问联系电话。
- 缺少 `name`：最后询问客户称呼。
- 每一轮都抽取全部字段，已经获得的字段直接跳过。
- 不应机械地按照“姓名 → 电话 → 维修”逐项询问。

### 2. 抽取模型与对话模型分离

结构化抽取器只负责理解客户输入并返回 JSON，不负责生成对话。
用于向客户说话的模型独立运行，只在需要澄清、回答额外问题或处理异常时，
生成一句简短回复。

建议抽取器输出：

```json
{
  "name": null,
  "phone": null,
  "repair": "冷气不制冷",
  "intent": "provide_info",
  "fields_to_correct": [],
  "lang": "yue",
  "confidence": {
    "repair": 0.91
  },
  "evidence": {
    "repair": "部冷气有风但唔冻"
  }
}
```

`intent` 建议支持：

```text
provide_info
confirm
deny
use_ani
transfer
complaint
other
```

不能只相信模型返回的 `confidence`。是否接受字段应同时参考：

1. 模型置信度。
2. 对应的原文 `evidence`。
3. 后端确定性格式和业务校验。

开口的模型应满足：

- 每次最多生成一句话。
- 不得擅自承诺上门时间或维修结果。
- 不负责数据库写入或状态迁移。
- 不返回工具调用。
- 语言跟随客户当前使用的语言。

### 3. 精准字段修正

确认阶段不能在用户否认后清空全部资料，也不能在未清空错误字段时立即再次确认。

正确处理方式：

```text
客户：“电话唔啱，係98765432”
→ 只更新 phone
→ 保留 name 和 repair
→ 重新生成完整确认
```

```text
客户：“唔啱”
→ 询问：边样需要改？姓名、电话，定维修内容？
```

抽取结果中的 `fields_to_correct` 用于识别需要修改的具体槽位。

### 4. 槽位模型与验收规则

三个字段不再只保存字符串。每个槽位建议保存：

```text
value
status: missing | candidate | validated | confirmed
source: asr | ani | dtmf | operator
evidence
confidence
attempts
```

#### 姓名

- 支持中文姓名、姓氏加称呼以及英文名。
- 不能仅按 2–20 个字符判断，因为可能存在单字姓或英文名。
- 排除“喂、你好、明白、听唔到、先生、小姐”等无效值。
- 结合当前正在询问的字段和自报姓名上下文判断。

#### 电话

- 支持香港 8 位号码。
- 支持中国内地 11 位号码。
- 支持 `+852`、`+86` 等区号。
- ANI 经客户确认后可视为有效来源。
- 最终确认时应逐位读出号码。

#### 维修内容

- 至少包含设备、症状或地点中的有效信息。
- 单独的“坏咗”“唔得”信息不足，需要再追问设备或具体表现。
- 派单必须知道地点时，地点属于必要信息。
- 低可信字段不能进入最终确认。

### 5. ANI 与 DTMF

正式电话平台接入后支持以下退路：

#### ANI

电话平台提供 Caller ID 后，可以询问：

> 之后用你而家嘅来电号码联络你，得唔得？

客户回答“就用来电嗰个”时，抽取器返回：

```json
{
  "intent": "use_ani"
}
```

系统确认 ANI 可用后，不再要求客户口述电话号码。

#### DTMF

电话号码连续两次 ASR 失败后，提示：

> 请用手机键盘输入联系电话，以井号结束。

DTMF 依赖 SIP、Twilio 或电话网关提供按键事件。当前浏览器 Demo
没有真实 ANI 和 DTMF，现阶段只设计接口与状态，接入电话平台时再实现。

### 6. 沉默、插话和人工升级

下一版状态机：

```text
GREETING
COLLECTING
CONFIRMING
WRITING
HOLD
ESCALATING
COMPLETED
```

#### 插话

- 播放录音或 TTS 时，客户开始说话应立即停止播放。
- 保留客户开头的语音，不能丢失前 100–300ms。
- 将完整客户话语送入 ASR 和字段抽取。

#### 沉默

- 等待 5–6 秒无声：播放“你仲喺度吗？”
- 再次无声：重复当前问题一次。
- 仍然无响应：进入 `ESCALATING` 或结束通话。

#### 转人工

以下情况直接进入 `ESCALATING`：

- 客户明确说“转人工、找经理、投诉”。
- 同一槽位连续三次无法获得有效值。
- ASR、LLM、TTS 或数据库多次失败。
- 客户情绪激烈或问题不属于维修收单范围。

当前可以先产生内部事件：

```json
{
  "type": "escalate",
  "reason": "phone_retry_exceeded",
  "slots": {},
  "transcript": []
}
```

接入实际电话平台后再完成真正的人工转接，并把已有槽位、转写及录音信息
同步给人工坐席。

### 7. 维修内容的收集边界

第一版目标是形成一张可执行的维修订单，而不是在电话中完成完整工勘。

维修内容优先包含：

- 什么设备。
- 出现什么问题。
- 在哪里（派单需要时）。

持续时间、紧急程度等信息能自然抽取就保存，不应逐项强制询问。
最多追加询问一个最关键的缺失信息，通常是设备或故障表现。

### 8. 多语言跟随

抽取器同时返回：

```text
lang: yue | cmn | en
```

本地录音目录：

```text
audio/
  yue/
  zh/
  en/
```

语音回复选择顺序：

```text
当前客户语言的本地录音
→ 没有对应录音时使用同语言动态 TTS
→ 不擅自切换或宣布切换语言
```

动态 TTS 应使用与客户语言匹配的 `language_boost`：

- 粤语：`Chinese,Yue`
- 普通话：`Chinese`
- 英文：`English`

### 9. 固定录音与动态 TTS

固定话术优先使用本地预制录音：

```text
greeting.wav
ask_need.wav
ask_repair.wav
ask_phone.wav
ask_name.wav
retry_repair.wav
retry_phone.wav
retry_name.wav
ask_correct_field.wav
ask_still_there.wav
order_saved.wav
```

处理等待期间可以播放短承接语：

```text
ack_checking.wav
ack_got_it.wav
ack_ok.wav
ack_writing.wav
```

确认语不建议采用“固定录音 + 多段变量 TTS”的碎片拼接，因为容易出现语调和
音量断裂。推荐：

1. 先播放固定承接语：“好嘅，我帮你确认一下。”
2. 再使用一次动态 TTS 生成完整确认句。

### 10. 推荐完整状态流程

```text
GREETING
  → 播放通用问候
  → 如果客户尚未表达来意，播放 ask_need.wav

COLLECTING
  → 每轮执行 ASR
  → 结构化抽取全部字段、意图、语言和修正目标
  → 后端校验字段并保存 evidence
  → 优先级 repair > phone/ANI > name
  → 已有并通过校验的字段直接跳过
  → 同槽第 2 次失败：播放 retry_*.wav 或由 LLM 生成一句澄清
  → 同槽第 3 次失败：进入 ESCALATING

CONFIRMING
  → 承接语后使用整句 TTS 复述三个字段
  → 电话号码逐位读出
  → yes：进入 WRITING
  → no + 指定字段：仅重置对应槽位，返回 COLLECTING
  → no 且未指定字段：询问要修改哪一项

WRITING
  → 数据库写入成功：进入 COMPLETED
  → 第一次失败：进入 HOLD，播放等待提示并重试一次
  → 再次失败：进入 ESCALATING

ESCALATING
  → 产生人工升级事件
  → 携带 slots、transcript、recording 和失败原因
  → 电话平台可用时执行真正转接

COMPLETED
  → 播放完成和结束语
  → 结束或等待客户补充
```

### 11. 实施优先级

按以下顺序实现：

1. 调整字段优先级为 `repair → phone/ANI → name`。
2. 修复确认阶段的精准纠错逻辑。
3. 增加槽位状态、字段校验、证据和尝试次数。
4. 扩展结构化抽取 JSON Schema。
5. 增加沉默检测和失败重试。
6. 增加粤语、普通话和英文录音目录路由。
7. 完善数据库写入失败的 `HOLD` 与重试。
8. 最后接入 ANI、DTMF 和真正的人工转接。

## 下一版结论

下一版采用“确定性状态机 + 结构化抽取器 + 少量生成式回复”的混合架构：

- 状态机负责流程和安全边界。
- 抽取器负责把客户语音转换为结构化字段和意图。
- 后端校验负责决定字段是否可接受。
- 本地录音负责固定问题和等待承接。
- 动态 TTS 负责包含客户资料的完整确认句。
- 生成式对话只用于澄清和异常场景。

`confidence` 不能单独决定字段是否有效；DTMF、ANI 和人工转接依赖后续电话平台；
确认句优先使用整句 TTS，避免碎片拼接造成不自然的听感。

## 电话校验反馈与开场语言策略

### 1. 区分“没有听到电话”和“听到无效电话”

系统不能把所有电话识别失败都统一处理成 `phone = null`，否则无法给客户准确反馈。

建议抽取和校验结果保留：

```json
{
  "phone": null,
  "phone_candidate": "123456789",
  "phone_error": "invalid_length",
  "phone_evidence": "一二三四五六七八九"
}
```

`phone_error` 建议支持：

```text
not_provided       # 客户没有说电话号码
not_understood     # ASR结果无法形成号码
invalid_length     # 数字位数不符合规则
invalid_format     # 包含无法接受的格式
low_confidence     # 候选号码可信度不足
```

处理原则：

- 不直接丢弃无效候选值。
- 保留原始证据，便于日志排查。
- 无效候选值不能进入最终确认。
- 根据具体错误原因播放不同的提示语。

#### 粤语提示

没有听到电话号码：

> 唔好意思，我未听到联系电话，请逐个数字讲一次。

听到但号码位数错误：

> 你啱啱讲嘅电话号码位数唔啱，请逐个数字再讲一次。

无法确认识别结果：

> 唔好意思，我确认唔到个电话号码，请讲慢少少再讲一次。

#### 普通话提示

没有听到电话号码：

> 不好意思，我没有听到联系电话，请逐位说一次。

听到但号码位数错误：

> 您刚才说的电话号码位数不正确，请逐位再说一次。

无法确认识别结果：

> 不好意思，我无法确认电话号码，请放慢一点再说一次。

#### 英文提示

> Sorry, I could not confirm the phone number. Please say each digit slowly.

连续两次语音识别失败后，正式电话平台可切换到 DTMF：

> 请使用手机键盘输入电话号码，以井号结束。

当前浏览器 Demo 暂不具备真实 DTMF 事件，先保留状态和接口。

### 2. 电话号码验收规则

第一版支持：

```text
香港号码：8 位
中国内地手机号码：11 位，通常以 1 开头
香港区号格式：852 + 8 位
内地区号格式：86 + 11 位
```

电话号码应保存：

```text
raw_text          # 用户原话或ASR文本
candidate         # 解析出的数字候选
normalized_value  # 规范化号码
validation_error  # 校验错误
source            # asr | ani | dtmf | operator
confidence
attempts
```

最终确认时将号码逐位读出，不能快速连读。

### 3. 开场语言策略

不建议每通电话都强制增加一轮独立语言选择，因为会增加通话时长和客户操作成本。

推荐采用：

```text
通用多语言开场
→ 根据客户第一句话自动识别语言
→ 检测不确定时才询问语言
→ 确定后锁定 session_language
```

推荐开场：

> 你好，广东话、普通话或者 English 都可以。请问有什么可以帮到你？

如果语言检测不确定，再询问：

> 请问想用广东话、普通话，还是英文？

客户也可以在开始时直接回答：

```text
广东话
普通话
English
```

会话中保存：

```text
session_language: yue | cmn | en
language_source: explicit | detected
language_confidence
```

### 4. 语言锁定和切换

语言确定后：

- 固定录音从对应语言目录读取。
- 动态 TTS 使用对应 `language_boost`。
- LLM 使用相同语言生成回复。
- 不需要每轮重新切换语言。
- 不主动说“现在为您切换语言”。
- 客户明确要求更换语言时才更新 `session_language`。

目录建议：

```text
audio/
  yue/
    greeting.wav
    ask_repair.wav
    ask_phone.wav
    invalid_phone.wav
  zh/
    greeting.wav
    ask_repair.wav
    ask_phone.wav
    invalid_phone.wav
  en/
    greeting.wav
    ask_repair.wav
    ask_phone.wav
    invalid_phone.wav
```

TTS语言增强映射：

```text
yue → Chinese,Yue
cmn → Chinese
en  → English
```

### 5. 语言回退策略

```text
明确语言选择
→ 使用该语言

没有明确选择
→ 使用ASR和文本特征自动检测

检测置信度不足
→ 播放语言选择问题

对应语言没有本地录音
→ 使用同语言动态TTS

动态TTS失败
→ 播放通用兜底录音或进入人工升级
```

### 6. 更新后的开场流程

```text
GREETING
  → 播放多语言通用开场
  → 客户直接描述问题：
       检测并锁定语言
       抽取维修、电话、姓名
       按 repair > phone/ANI > name 补问缺失字段
  → 客户明确选择语言：
       锁定 session_language
       用对应语言询问维修需求
  → 语言无法判断：
       询问广东话、普通话还是英文
```

### 7. 对当前实现的影响

下一步代码调整应包括：

1. 抽取结果新增 `phone_candidate` 和 `phone_error`。
2. 电话校验失败时，不再统一播放普通的 `ask_phone`。
3. 根据错误原因选择 `invalid_phone` 或 `retry_phone`。
4. 会话对象新增 `session_language` 及语言来源。
